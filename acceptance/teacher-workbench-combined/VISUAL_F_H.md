## Evidence and method

Compared the actual newly captured Workbench v2.2 prototype in `prototype-01` with the pinned production candidate in `application-01`, reading each original image at 1440×1000, 1024×768, 390×844, 320×844 and native 200%. Native comparisons use the complete original `-native200-cdp.png` surfaces, not crops, edited pixels, or CSS zoom. The receipts for the relevant native states record outer width 1440, inner width 708, height 454, DPR 2, root CSS zoom 1 and visual-viewport scale 1. Each selected application state reports no captured browser error and no document overflow. These measurements support the visual observations; they do not by themselves establish usability or parity.

The application fixture has seven authorized assignments, sixteen decisions and five saved drafts. The prototype has different section, assignment, student and response counts. The concern concerns transmission delay in both, but the actual approved application category description, saved observations and denominator differ. These count/title differences are not defects and were not made to match the prototype artificially.

## Ranked remaining findings

1. **P2 — Concerns native 200% density still differs materially.** The application stacks Student work subnavigation, the pane tabs, and a second Investigation heading before the actual concern. The pane tabs occupy CSS y120–163 and the redundant heading y163–214; fixed bottom navigation begins at y389. This leaves only 175 CSS pixels for the initial investigation content. The complete original zoom image shows the primary action and caution below the initial viewport, while the prototype shows both. This is a visual hierarchy/density issue; scrolling access is not disproven. It is present in the integrated owner code and is not demonstrated to be a merge regression. Compare [application](application-01/learning-insights-native200-cdp.png) with [prototype](prototype-01/learning-insights-native200-cdp.png).

2. **P2 — Overview retains functional prototype gaps despite the restored structures.** Section filter chips are absent; evidence-origin filtering is a different operation. Priority rows use concept-level partial/incorrect or uncertain counts rather than the prototype's named concern hypothesis, repeated/contrary evidence and linked intervention status. Existing source-owner `overview/verification/parity.json` declares these differences. They cannot be attributed to the seven-versus-four-assignment fixture difference. The reviewer must explicitly accept the narrower behavior or keep it open; do not call R04 fully prototype-equivalent. Compare [desktop application](application-01/overview-1440x1000.png) and [prototype](prototype-01/overview-1440x1000.png).

3. **P2 — Concern investigation still omits prototype comparison/class-grid affordances.** The populated application has useful original-evidence links, source context and intervention preparation, but no equivalent of the prototype's visible “See it in the class grid” action or per-response side-by-side comparison selection. The H parity document expressly retains Evidence as the full inspection path and omits the separate comparison capability. This is a declared capability difference, not a claim that saved evidence is inaccessible, and not a newly invented integration requirement. Compare [application](application-01/learning-insights-1440x1000.png) and [prototype](prototype-01/learning-insights-1440x1000.png).
