## Final reading-recovery integration guards

These are client presentation/recovery guards; the server remains the authority for whether an answer or evaluation may proceed.

1. Explicit passage selection immediately blocks the current answer controls while the existing reader opens, displays and acknowledges it. The summary contains passage titles/identifiers rather than unacknowledged source excerpts.
2. The reader reports its existing `confirmedId`, busy state and error. A confirmed receipt triggers the existing read-only session refresh. Unblocking requires no server `pending_reading`, the same current selection object, a non-busy local reader and the same confirmed receipt. A delayed refresh for an older passage cannot unblock a newer selection.
3. A failed progress refresh leaves recovery visible. Explicit **Refresh saved progress** uses the same local receipt/selection and server-pending checks, without reopening or re-acknowledging a passage blindly.
4. Reopening an already-confirmed passage is allowed to reconcile through a read-only refresh; the duplicate-confirmed shortcut was removed so the composer cannot remain locally blocked merely because the reader retained its original receipt.
5. The final root integration change derives `readingBlocksCurrent = readingAttempt === lastId && readingBlocked`. That derived value is used at the composer, initial evaluation and retry-evaluation controls. An old local reading failure cannot block a newly authorized attempt; server `pendingReading`, busy state and evaluation retry eligibility remain independent gates.
6. Reading opened while inspecting an older saved page is explicitly described as applying to the current question. It does not rewrite that older page's assistance history.

### Stale reader-refresh protection and reachable recovery

A reading GET could otherwise resolve after a newer passage, manual refresh, answer or polling result and replace the current local view before the caller's unblocking guard ran. The final source keeps one accepted-view setter and increments a local applied-view revision whenever that setter accepts a snapshot. It adds an optional `shouldApply` predicate to the existing `refresh` function, checked before answer-recovery reconciliation or view mutation. Calls without that predicate retain their existing behavior; callers explicitly handle the nullable skipped result.

The reader captures the applied-view revision and its current selection/confirmed receipt. Its refresh may apply only while that revision, selection and receipt still match, the reader is non-busy and no session operation is in progress. A skipped result cannot unblock controls. An accepted result may unblock only if it advanced the view revision exactly once and the same reading still applies with no server-pending passage. A failure from a superseded reader refresh cannot post a recovery error over newer work. This is a stale-response guard within the existing session owner; it adds no transport, request identity, backend state or second controller.

While reading still blocks the current question, the existing **Refresh saved progress** control remains reachable outside the switchable panes, including the ordinary answer phase. A status notice explains that local reading progress is not yet confirmed without claiming a failed receipt or a running retry. This also covers an automatic reader refresh discarded after another snapshot was accepted. Successful newer reconciliation removes the blocker and notice; a skipped old response cannot restore them. When the existing error notice already contains the refresh control, it is not duplicated in session actions.
