# Teacher and authoring acceptance matrix

This is a reusable acceptance design, not a pass report. It was mapped from source `723ed6fea41138b604a9d333ebcd4a07b2202c36` on main. Execute the same cases separately against each exact target SHA: main/release candidate, PR #116, and each later Lessons or Assignments branch. A passing result on one target does not carry to another target or a hosted release.

Use the isolated runner and target manifest for environment setup. The commands below run inside that target's application container with its disposable PostgreSQL database. They must never target a teammate's stack or the hosted application. All material and identities are fictional. Both `OPENAI_API_KEY` and `OPENAI_MODEL` must be empty in the application process and check process. No `--live`, `--live-only`, `questions:live`, `eval:live`, or new actual-model execution is authorized.

Executed later-target results are in the [PR117 report](PR117_REPORT.md),
[PR118 report](PR118_REPORT.md), and [combined report](COMBINED_REPORT.md).

## Evidence recorded for every case

Record target label, full source SHA, dirty-state status, build/image identifier, database/project identifier, origin, execution time, configuration category, fixture identity, command or browser steps, observed result, and pass/fail/unrun status. For browser cases also record route, viewport, screenshot path, and whether real keyboard/zoom behavior was observed. Use separate categories for deterministic fixtures, provider-disabled integration, historical actual-model evidence, fresh actual-model evidence, and hosted verification.

For a teacher action, preserve assignment/class ID, concept ID, source and lesson versions, original attempt ID/text, accepted evaluation ID, displayed assistance, draft ID and saved revision, approved revision, approval ID, delivery ID, recipient IDs, and later follow-up session/attempt/evaluation IDs where available. Never replace these identities with a screenshot alone. Reports must not contain credentials or authentication cookies.

## Responsive and accessibility cases

Run the teacher workspace/evidence detail, intervention editor, materials/objectives/questions, lesson publication, assignment review, and corresponding student assignment/reading/follow-up pages at 1440×900, 1024×768, 390×844, and 320px width. Capture named screenshots for each tested page/state/viewport and record failures by exact target SHA.

Check navigation reachability, unintended horizontal overflow, long original answers, evidence list/detail transitions, source/question visibility, editable controls, recipient choices, approval/delivery controls, keyboard Tab/Shift+Tab/Enter/Space/Escape, visible focus, Back/Forward, refresh, scroll and focus restoration, and actual 200% browser zoom. A screenshot cannot prove keyboard operation, semantic accessibility, or screen-reader behavior. Mark screen-reader checks unrun unless actually performed with a screen reader. A responsive narrow viewport alone is not evidence that 200% zoom was tested.

## Replay caveats and ownership reporting

- Most integration suites deliberately retain immutable synthetic records; they are not cleanup tools. Use disposable target databases, not real data, and include run IDs in fixture labels.
- Prefer the combined uploaded/curated approval command for a fresh teacher journey. Standalone `interventions:approval` and `interventions:outcomes` expect an already persisted source draft selected through `CHECK_INTERVENTION_REPORT`; their default historical live-report paths may not match the isolated database.
- To prepare the standalone curated suites, set `CHECK_INTERVENTION_REPORT` to a new fixture-report path, run default `interventions:check`, and pass the same path to `interventions:http`, `interventions:approval`, or `interventions:outcomes`. Never reuse another target's report/IDs. Restart only the acceptance app between login-heavy suites as required.
- `interventions:outcomes` can later verify its saved outcome fingerprints across a database/application restart with its documented `--verify-persistence` mode. Preserve its report and database together; do not treat a missing report as success.
- A defect report contains target SHA, configuration category, fixture IDs, exact reproducible steps, expected/actual result, preserved-work status, screenshots/log references, severity and owning workstream. Notify the current Workbench, Lessons, Assignments, Student/PR #113, or R2 owner without naming an invented teammate or applying a competing fix.
- Current-main release readiness and PR #116 merge readiness remain independent decisions. Any broken working fallback, lost original work, unauthorized evidence exposure, source/version mismatch, unintended grading, duplicate paid operation, or incorrect approval/delivery boundary is a release blocker. Pure shell/visual refactors may be deferred after submission when the known working main fallback remains verified. Unrun critical journeys are acceptance gaps, not passes.
