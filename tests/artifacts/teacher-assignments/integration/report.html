Frozen integration contracts

C2: progress → session → progress

/teacher/sessions/<sessionId>?
  returnTo=progress
  &assignment=<authorized assignment>
  &origin=<current evidence origin>
  &progressStudent=<original selected student, optional>
  &progressConcept=<original selected concept, optional>
  &progressView=grid|concepts|questions|sessions
  &pane=grid|details
  &class=<current authorized class filter, optional>
  &status=<current status filter>
  &attempt=<target attempt, when applicable>
  #attempt-<target attempt>

The target session identifies the student whose work is opened. The link deliberately omits target student and concept query fields: the session route authorizes the actual record. The namespaced fields preserve the teacher's original selection even when a Questions or Study sessions row belongs to another student.

The shared receiver returns to /teacher/assignments with view=progress, maps progressStudent → student and progressConcept → concept, and preserves assignment, origin, progress view, pane and list filters. It must validate the return student against the authorized assignment roster and the return concept against its exact approved version. Return context never grants record access.

Return view Focus target
Details pane cell-evidence
Grid with a selected student and/or concept ap-selection-<student or all>-<concept or all>
Concepts with a selected concept ap-selection-all-<concept>, the visible concept column rather than an absent student/concept cell.
Questions, Study sessions, or no visible selection target progress-main

The progress region declares data-workspace-restoration="page". Only fixed or context-derived hash targets are accepted; no arbitrary selector is used. This avoids a second competing shared restoration controller.

C5: published lesson → new classroom assignment

/teacher/assignments/new?lesson=<exact lesson ID>&version=<full published version>[&class=<authorized class ID>]

The current receiver rejects orphan versions, unknown exact pairs and foreign classes, then resolves the selected immutable content through existing authorized services. Legacy lesson-only links select that lesson's first available published version; the unscoped picker selects the first catalog item. This compatibility behavior does not apply to exact two-field handoffs.

Creation remains an inactive assignment. Activation is a separate review action. The recovered request retains its original class, title, instructions and idempotency identity. Merely opening or returning to the builder must not create, activate or rewrite a lesson.

V05: one gutter, shared shell and full-width progress

With PR #120's documented shell, normal content uses 28px horizontal gutters on desktop, 14px at widths up to 800px and 12px at widths up to 360px. Only the resolved progress workspace cancels the outer shell inset. Its main heading/content restores the same gutter, while the desktop details column remains 380px wide. At 1440px the intended full-width frame is 1060px main + 380px details; this remains a source-derived expectation until captured.

Integration dependencies and limits

  • Shared C receiver: accept the frozen namespaced progress return fields, authorize the opened session/attempt separately, validate return roster/concept scope, and render “Back to class progress” with the correct focus hash. Its commit must be present in the candidate.
  • Lessons E outgoing handoff: emit the exact published lesson/version pair to the new-assignment receiver. Its commit and actual rendered link must be verified; the receiver alone does not complete C5.
  • PR #120 shell: retain its documented 28/14/12px inset and page-owned restoration contract. The assignment page consumes these; it does not edit the shared shell or mount a competing pane controller.
  • Runtime isolation: create a fresh project, database volume, ports/networks and outside-source state after shared-lock coordination. Existing acceptance runners and browser helpers are pinned to old projects and old source/fixture receipts; changing their state directory alone does not create isolation.
  • Synthetic scope: blank model providers and fictional fixtures only. Expanded class fixtures, default captures and published-density fixtures are different database states. The retained nineteen-question published fixture and 24-student expanded class fixture are not equivalent to the prototype's fifteen questions and eighteen students.

No paid model call, live student data, real agentic acceptance, screen-reader acceptance or automatic merge is claimed.
